# Стандарт кодування проєкту RepairService

Версія 1.0 · ЛР № 1 · автор: Новиков Роман, група 471

## 1. Загальні положення

1.1. Стандарт обов'язковий для всього коду C# у рішенні RepairService
(проєкти RepairService.Core і RepairService.App).

1.2. Мова коду й ідентифікаторів — англійська; мова коментарів,
XML-документації, повідомлень комітів і рядків для користувача — українська.

1.3. Платформа — .NET 8, C# останньої версії (`LangVersion = latest`),
nullable-аналіз увімкнено (`Nullable = enable`).

1.4. Проєкт збирається командою `dotnet build` з 0 попереджень і 0 помилок.
Код, що додає хоча б одне попередження, до гілки `main` не потрапляє.

1.5. Правило аналізатора вимикається тільки в `.editorconfig` і тільки з
коментарем-обґрунтуванням у попередньому рядку. Точкове придушення
`[SuppressMessage]` — не більше ніж двічі на весь проєкт, з `Justification`.

## 2. Іменування

| Сутність | Конвенція | Приклад | Антиприклад |
|---|---|---|---|
| Клас, запис | PascalCase, іменник | `RepairLine` | `repairline` |
| Інтерфейс | I + PascalCase | `IRepairRepository` | `Repository` |
| Метод | PascalCase, дієслово | `CalculateTotal` | `calc` |
| Властивість | PascalCase, іменник | `UnitPrice` | `GetUnitPrice` |
| Приватне поле | _ + camelCase | `_lines` | `m_Lines` |
| Локальна змінна, параметр | camelCase | `totalAmount` | `ta` |
| Константа | PascalCase | `MaxLineCount` | `MAX_LINES` |
| Перелічення | PascalCase, однина | `RepairStatus` | `RepairStatuses` |
| Простір імен | Проєкт.Шар.Тека | `RepairService.Core.Domain` | `Core.domain` |

2.1. Скорочення в іменах заборонені, крім загальновживаних (`Id`, `Sku`,
`Url`); `cnt`, `usrNm`, `tmp` — порушення.

2.2. Булеві властивості й змінні починаються з `Is`, `Has` або `Can`
(`IsRegular`, `IsPart`).

2.3. Ім'я файлу збігається з ім'ям єдиного публічного типу в ньому
(`RepairRequest.cs` містить `RepairRequest`).

## 3. Форматування

3.1. Відступ — 4 пробіли; табуляція заборонена. Для `.csproj`, `.props`,
`.json`, `.yml` — 2 пробіли.

3.2. Довжина рядка — не більше ніж 100 символів.

3.3. Фігурні дужки — стиль Allman (відкривна дужка на новому рядку);
дужки обов'язкові навіть для однієї інструкції в тілі `if`, `for`, `while`.

3.4. Між членами класу — рівно один порожній рядок; два порожні рядки
поспіль заборонені.

3.5. Директиви `using` — на початку файлу, поза простором імен, `System.*`
першими; невживані `using` видаляються.

3.6. Простір імен — файлового рівня (`namespace RepairService.Core.Domain;`).

3.7. В ініціалізаторі об'єкта кожна властивість — на окремому рядку.

3.8. Файл закінчується одним символом нового рядка; пробіли в кінці рядків
заборонені. Кодування файлів — UTF-8.

3.9. Порядок членів класу: поля → конструктори → властивості → методи;
усередині групи — `public` перед `private`.

## 4. Коментарі та документація

4.1. Коментар пояснює «чому», а не «що». Коментар, який переказує код,
видаляється.

```csharp
// погано: коментар переказує код
// додаємо суму рядка до загальної суми
sum += line.Amount;

// добре: коментар пояснює причину рішення
// гарантійний ремонт оплачує виробник, тому клієнт платить 0
if (request.IsWarranty)
{
    return 0m;
}
```

4.2. Кожен публічний тип має XML-коментар `/// <summary>` одним реченням.
З ЛР № 4 XML-документація обов'язкова і для всіх публічних членів бібліотеки
RepairService.Core.

4.3. Закоментований код у репозиторій не потрапляє — для історії є Git.

4.4. Позначки `TODO` дозволені лише з номером роботи, у якій їх буде
закрито: `// TODO(ЛР 3): перевірити кількість > 0`.

## 5. Структура проєкту

5.1. Рішення складається з двох проєктів: `RepairService.Core` (бібліотека
класів — уся логіка предметної області) і `RepairService.App` (консольний
застосунок — тільки введення й виведення).

5.2. `RepairService.Core` не звертається до `Console`; залежність тільки
одна: App → Core.

5.3. Доменні типи лежать у теці `RepairService.Core/Domain`, один тип —
один файл.

5.4. Гроші — тільки `decimal`; дата й час — `DateTimeOffset`, `DateOnly` або
`TimeOnly`; `double` і `DateTime` для них не використовуються.

5.5. Спільні налаштування збірки задаються в `Directory.Build.props`, а не
в кожному `.csproj`. Версію SDK закріплює `global.json`.

## 6. Правила комітів

6.1. Повідомлення — за Conventional Commits: `тип: коротка суть` у
наказовому способі, українською, до 72 символів. Типи: `feat`, `fix`,
`docs`, `chore`, `style`, `refactor`, `test`.

6.2. Один коміт — одна завершена зміна; після кожного коміту проєкт
збирається без попереджень.

6.3. Теки `bin` і `obj`, файли `*.user` і локальні дані (`data/*.local.json`)
до репозиторію не потрапляють — їх відсікає `.gitignore`.

6.4. Кінець кожної лабораторної роботи позначається міткою: `lab1`, `lab2`, …
