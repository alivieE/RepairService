# Специфікація RepairService

Застосунок для приймальника сервісного центру: облік заявок на ремонт
пристроїв, розрахунок дедлайну й вартості, проведення заявки станами
та звіт про прострочені заявки.

## 1. Межі системи

| Входить | Свідомо не входить |
|---------|--------------------|
| облік заявок, позицій, клієнтів і прейскуранта | платіжний термінал, фіскальні чеки |
| дедлайн ремонту за пріоритетом заявки | графік роботи майстрів і робочі дні |
| вартість робіт і деталей з надбавкою за терміновість | облік складу деталей і закупівлі |
| проведення заявки станами за таблицею переходів | сповіщення клієнта SMS чи поштою |
| пошук заявок за станом, клієнтом і пріоритетом | розмежування прав користувачів |
| звіт «прострочені заявки» на дату | графічний інтерфейс, вебдоступ |
| збереження даних у файлі JSON | база даних |

## 2. Словник домену

| Термін | Ідентифікатор у коді | Значення |
|--------|----------------------|----------|
| заявка | `RepairTicket` | документ на ремонт пристрою; має стан, пріоритет і позиції |
| позиція заявки | `RepairWork` | робота або деталь: код, кількість, ціна за одиницю |
| вид позиції | `LineKind` | `Work` — робота майстра, `Part` — деталь |
| клієнт | `Customer` | людина, що здала пристрій у ремонт |
| прейскурант | `ServiceItem` | довідник робіт і деталей з цінами |
| пріоритет | `TicketPriority` | `Low`, `Normal`, `High`, `Urgent` |
| стан заявки | `TicketStatus` | `Received`, `InWork`, `Ready`, `Issued`, `Rejected` |
| дата прийняття | `RepairTicket.CreatedAt` | день, коли пристрій прийнято в ремонт |
| дедлайн | `RepairTicket.Deadline` | дата, до якої ремонт має бути завершено |
| строк ремонту | `PriorityRules.DaysFor` | кількість днів від прийняття до дедлайну |
| надбавка за терміновість | `PriorityRules.SurchargeOf` | частка, на яку зростає вартість робіт |
| вартість заявки | `RepairTicketService.TotalOf` | роботи з надбавкою плюс деталі, грн |
| прострочена заявка | `OverdueReport` | незавершена заявка, дедлайн якої минув |
| оплата при видачі | `RepairTicketService.Pay` | оплата, після якої пристрій видається |
| порушення правила | `DomainRuleException` | виняток домену з ідентифікатором правила |


## 3. Сценарії використання

### UC-01. Прийняти заявку (сценарій-ядро варіанта)

- **Дійова особа:** приймальник.
- **Мета:** оформити пристрій у ремонт з відомим дедлайном.
- **Передумова:** клієнт є в довіднику.
- **Основний перебіг:**
  1. Приймальник вводить номер клієнта.
  2. Приймальник вводить модель пристрою.
  3. Приймальник обирає пріоритет: низький, звичайний, високий або терміновий.
  4. Система перевіряє введені дані.
  5. Система створює заявку в стані Received, датою прийняття ставить сьогоднішню,
     а дедлайн обчислює за пріоритетом (таблиця 1).
  6. Система показує номер заявки й дедлайн і робить запис до журналу рівня Information.
- **Альтернативи:**
  - 1а. Клієнта не знайдено — повідомлення, заявка не створюється, запис рівня Warning.
  - 2а. Модель пристрою порожня — повідомлення й повторний запит.
  - 3а. Пріоритет не з переліку — повідомлення й повторний запит.
- **Постумова:** існує нова заявка в стані Received з датою прийняття й дедлайном.
- **Правила:** таблиця 1.
- **Тести:** `Accept_ValidInput_CreatesReceivedTicket`, `Accept_UnknownCustomer_Throws`,
  `Accept_UrgentPriority_DeadlineNextDay`.

### UC-02. Провести заявку станами (сценарій-ядро варіанта)

- **Дійова особа:** майстер.
- **Мета:** відобразити в системі хід ремонту.
- **Передумова:** заявка існує.
- **Основний перебіг:**
  1. Майстер вводить номер заявки.
  2. Система показує поточний стан заявки.
  3. Майстер обирає дію: почати ремонт, завершити ремонт або відмовити в ремонті.
  4. Система перевіряє дію за таблицею переходів (таблиця 2).
  5. Система змінює стан і робить запис до журналу рівня Information.
- **Альтернативи:**
  - 1а. Заявку не знайдено — повідомлення, повернення до меню.
  - 4а. Перехід заборонено (наприклад, завершити ремонт, який не почато) —
    операцію відхилено, стан не змінюється, запис рівня Warning.
  - 4б. Почати ремонт заявки без жодної позиції — операцію відхилено, запис рівня Warning.
- **Постумова:** стан заявки змінено згідно з таблицею 2.
- **Правила:** таблиця 2.
- **Тести:** `StartWork_ReceivedWithLines_BecomesInWork`, `Issue_FromInWork_Throws`,
  `Reject_AfterIssued_Throws`.

### UC-03. Додати роботу або деталь до заявки

- **Дійова особа:** приймальник.
- **Мета:** зафіксувати, що саме і за якою ціною буде зроблено.
- **Передумова:** заявка існує і перебуває в стані Received.
- **Основний перебіг:**
  1. Приймальник вводить номер заявки.
  2. Приймальник вводить код роботи або деталі з прейскуранта.
  3. Приймальник вводить кількість.
  4. Система знаходить позицію прейскуранта й фіксує її поточну ціну.
  5. Система додає позицію до заявки й показує нову вартість (таблиця 1).
- **Альтернативи:**
  - 1а. Заявка вже не в стані Received — операцію відхилено, запис рівня Warning.
  - 2а. Коду немає в прейскуранті — повідомлення й повторний запит.
  - 3а. Кількість не є цілим числом більше 0 — повідомлення й повторний запит.
- **Постумова:** позиція додана до заявки з ціною на момент додавання;
  зміна прейскуранта не змінює вже доданих позицій.
- **Правила:** таблиця 1.
- **Тести:** `AddLine_UnknownCode_Fails`, `AddLine_AfterStartWork_Throws`.
