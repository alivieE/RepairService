# 1. Сфера дії, рівні обов’язковості, глосарій

## 1.1. Сфера дії

Стандарт поширюється на весь код C# рішення RepairService, який пишуть
і змінюють члени команди.

| Проєкт | Що містить | Як діє стандарт |
|---|---|---|
| `RepairService.Core` | логіка предметної області, сервіси, правила | повністю |
| `RepairService.App` | консольний застосунок: введення й виведення | повністю |
| `RepairService.Tests` | модульні тести ядра | повністю, з винятками C-07 і N-16 |
| `tests/Legacy.Tests` | характеризаційні тести успадкованого модуля | так само, як `RepairService.Tests` |

Стандарт **не поширюється** на:

- `src/Legacy` — успадкований модуль із ЛР6. Аналізатори для нього вимкнено
  у файлі `RepairService.Legacy.csproj`, діє лише форматування `dotnet format`.
  Модуль приводять до стандарту за правилом бойскаута (розділ 7.3);
- згенерований код (`obj/`, файли `*.g.cs`, `*.Designer.cs`);
- гілки-пісочниці з префіксом `sandbox/`, які ніколи не зливаються в `main`;
- документацію в `docs/`, для якої діє лише правило F-03 (кодування й кінець файлу).

Стандарт діє з **16.11.2026**, поточна версія — **2.0.0**. Попередня
версія 1.0 (ЛР1) мала 30 пунктів без рівнів і без обґрунтувань.
Власник стандарту — Новиков Роман, супровідник репозиторію. Власник стежить,
щоб текст стандарту збігався з файлами `.editorconfig` і
`Directory.Build.props`, і веде журнал рішень `docs/decisions`.

## 1.2. Рівні обов’язковості

| Рівень | Значення | Наслідок порушення | Діагностика |
|---|---|---|---|
| **ОБОВ’ЯЗКОВО** | виконують завжди | збірка падає або зміну не приймають на огляді | `error` |
| **РЕКОМЕНДОВАНО** | виконують, якщо немає вагомої причини вчинити інакше | зауваження на огляді; причину відступу пишуть у коментарі | `suggestion` |
| **ДОПУСКАЄТЬСЯ** | обидва варіанти прийнятні | зауваження не роблять | `silent` або правило не вмикається |
| **ЗАБОРОНЕНО** | конструкція в проєкті не вживається | збірка падає або зміну не приймають на огляді | `error` |

У рішенні ввімкнено `TreatWarningsAsErrors`, тому діагностика рівня
`warning` теж зупиняє збірку. Щоб рівень у файлі однозначно відповідав
рівню в тексті, `warning` у `.editorconfig` не використовується зовсім:
правило, що зупиняє збірку, записане як `error`, а рекомендація — як
`suggestion` (рішення ADR-002).

Обов’язковими зроблено переважно правила, які перевіряє машина: людина на
огляді втомлюється, а збірка — ні. Підсумок розподілу наведено в
`CODING_STANDARD.md`.

## 1.3. Нумерація правил

Кожне правило має незмінний ідентифікатор, щоб на огляді писати не «мені
не подобається», а «порушено N-07».

| Префікс | Група правил | Розділ |
|---|---|---|
| N | іменування | 2 |
| F | форматування й структура файлу | 3 |
| C | коментарі й документація | 3 |
| D | дані й типи, гроші й дати | 4 |
| X | правила предметної області варіанта № 11 | 4.5 |
| S | керуючі конструкції та складність | 5 |
| A | машинна частина | 6 |
| R | пункти чеклісту огляду | 7, `docs/review-checklist.md` |

Номер скасованого правила більше не використовують: якщо скасовано D-09,
наступне нове правило групи D отримає номер після останнього наявного.

## 1.4. Шаблон запису правила

Усі правила оформлено за одним шаблоном: ідентифікатор — формулювання —
рівень — обґрунтування — порушення — дотримання — перевірка.

> **X-02. Дедлайн заявки обчислюють лише через `PriorityRules.DeadlineOf`.**
> - **Рівень:** ОБОВ’ЯЗКОВО.
> - **Обґрунтування:** строк ремонту залежить від пріоритету за таблицею 1
>   специфікації; якщо додавати дні «на місці», то після зміни таблиці
>   частина коду рахуватиме за старими строками.
> - **Порушення:** `ticket.Deadline = createdAt.AddDays(2);`
> - **Дотримання:** `ticket.Deadline = PriorityRules.DeadlineOf(createdAt, priority);`
> - **Перевірка:** пункт R-07 чеклісту, тест `DeadlineOf_ByPriority_AddsDays`.

Поле «Перевірка» обов’язкове. Правило, для якого не можна назвати спосіб
перевірки (аналізатор, пункт чеклісту, тест), у стандарт не вноситься.

## 1.5. Глосарій предметної області

Одне поняття — один ідентифікатор. Перед тим як назвати новий тип, член
або змінну, перевіряють цю таблицю; нове поняття спочатку додають сюди
(правило N-17).

| Поняття | Ідентифікатор | Пояснення |
|---|---|---|
| заявка на ремонт | `RepairTicket` | документ: пристрій клієнта, позиції, стан, пріоритет |
| номер заявки | `RepairTicket.Id`, параметр `ticketId` | ціле число, більше за 0 |
| модель пристрою | `DeviceModel` | рядок, який вводить приймальник |
| позиція заявки | `RepairWork` | робота або запчастина з кількістю й ціною |
| вид позиції | `LineKind` | `Work` — робота майстра, `Part` — запчастина |
| код позиції | `Code` | код за прейскурантом, великими літерами, до 20 символів, наприклад `WKR-1` |
| ціна за одиницю | `UnitPrice` | `decimal`, грн, зафіксована на момент додавання |
| сума позиції | `Amount` | кількість × ціна, обчислювана властивість |
| клієнт | `Customer` | власник пристрою |
| позиція прейскуранта | `ServiceItem` | довідник робіт і запчастин із базовою ціною |
| пріоритет заявки | `TicketPriority` | `Low`, `Normal`, `High`, `Urgent` |
| стан заявки | `TicketStatus` | `Received`, `InWork`, `Ready`, `Issued`, `Rejected` |
| дата прийняття | `CreatedAt` | `DateOnly`, день, коли пристрій прийняли |
| дедлайн | `Deadline` | `DateOnly`, останній день строку ремонту включно |
| строк ремонту | `PriorityRules.DaysFor` | кількість календарних днів за пріоритетом |
| надбавка за пріоритет | `PriorityRules.SurchargeOf` | частка, на яку дорожчають роботи (не запчастини) |
| вартість заявки | `TotalOf` | роботи з надбавкою + запчастини, до копійок |
| прострочена заявка | `IsOverdueOn`, `OverdueReport` | стан `Received` або `InWork` і дата звіту пізніша за `Deadline` |
| оплата при видачі | `Pay` | сума не менша за вартість, після неї стан `Issued` |
| сховище заявок | `IRepairTicketRepository` | `Add`, `GetById`, `GetAll` |
| порушення правила домену | `DomainRuleException` | виняток із кодом правила, наприклад `ticket.payable` |
| поточна дата | `IClock` | залежність, через яку логіка дізнається «сьогодні» |

### Застарілі синоніми

Під час ЛР2–ЛР4 у ядрі з’явилися паралельні моделі заявки: наряд `WorkOrder`
(ЛР2), типи `Documents/*` (ЛР3) і `Domain/RepairTicket` (ЛР4). Через це одне
поняття зараз має кілька імен — саме та ситуація, від якої захищає глосарій.
Канонічні імена — ліворуч; праві в новому коді **заборонено** (N-17),
а наявні випадки погашаються як технічний борг TD-12 (рішення ADR-001).

| Канонічне ім’я | Застарілий синонім | Де лишився |
|---|---|---|
| `RepairTicket` | `RepairRequest`, `WorkOrder` | `Domain/RepairRequest.cs`, `WorkOrder.cs` |
| `RepairWork` | `RepairLine` | `Domain/RepairLine.cs`, `Documents/*` |
| `TicketStatus` | `RepairStatus` | `Domain/RepairStatus.cs`, `Documents/*` |
| `Customer` | `Client`, `ClientInfo` | `Domain/Client.cs`, `Documents/ClientInfo.cs` |
