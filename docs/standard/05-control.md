# 5. Керуючі конструкції та межі складності

## 5.1. Конструкції

**S-01. Передумови перевіряють на початку методу сторожовими умовами з раннім виходом.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** основний сценарій лишається на першому рівні
  вкладеності, а всі причини відмови видно одним блоком угорі.
- **Порушення:** `if (ticket != null) { if (ticket.Lines.Count > 0) { ... } }`
- **Дотримання:** `ArgumentNullException.ThrowIfNull(ticket);` і далі основна логіка без вкладення.
- **Перевірка:** R-09.

**S-02. Публічний метод перевіряє аргументи-посилання на `null`.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** `NullReferenceException` глибоко в методі не каже, який
  аргумент винен; `ArgumentNullException` з іменем параметра — каже.
- **Порушення:** `public static WorkOrder? FindById(List<WorkOrder> workOrders, ...)` без перевірки.
- **Дотримання:** перший рядок методу `ArgumentNullException.ThrowIfNull(workOrders);`
- **Перевірка:** CA1062, error.

**S-03. Глибина вкладеності — до 3 рівнів; глибшу вкладеність прибирають сторожовою умовою або виділенням методу.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** на четвертому рівні читач уже не пам’ятає, яка умова
  відкрила зовнішній блок. Межі наведено в таблиці 5.2.
- **Порушення:** `if` усередині `foreach` усередині `if` усередині `if`.
- **Дотримання:** сторожова умова або виділений метод.
- **Перевірка:** R-09.

**S-04. Ланцюг із трьох і більше `if – else if` за одним значенням замінюють `switch`-виразом або таблицею.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** `switch`-вираз читається як таблиця рішень і не дає
  забути присвоєння в одній із гілок.
- **Порушення:** чотири `if` за пріоритетом, кожен присвоює `days`.
- **Дотримання:** `PriorityRules.DaysFor` — `switch`-вираз на п’ять рядків.
- **Перевірка:** R-09.

**S-05. `switch` за переліченням закінчується гілкою `_ => throw new ArgumentOutOfRangeException(...)`.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** перелічення в C# може містити будь-яке ціле значення,
  тож без такої гілки новий член перелічення мовчки потрапить у «типову»
  поведінку. Тому IDE0010 (перелічити кожен член) придушено як надлишкове.
- **Порушення:** `_ => 0m,` у `SurchargeOf`.
- **Дотримання:** `_ => throw new ArgumentOutOfRangeException(nameof(priority), priority, "Невідомий пріоритет."),`
- **Перевірка:** R-09, тест `DaysFor_UnknownPriority_Throws`.

**S-06. `goto` заборонено.**
- **Рівень:** ЗАБОРОНЕНО.
- **Обґрунтування:** перехід на мітку ламає структуру блоків; у C# будь-який
  випадок без нього розв’язують виділенням методу чи `return`.
- **Порушення:** `goto retry;`
- **Дотримання:** цикл `while` з умовою виходу.
- **Перевірка:** R-09; пошук `git grep -n "goto "`.

**S-07. `continue` на початку тіла циклу для фільтра й `break` для виходу після знайденого елемента.**
- **Рівень:** ДОПУСКАЄТЬСЯ.
- **Обґрунтування:** `if (line.Kind == LineKind.Part) { continue; }` на першому
  рядку циклу зрозуміліший за вкладений блок; посеред довгого тіла ці
  оператори ховають потік керування, але така довжина вже порушує S-12.
- **Перевірка:** не перевіряють.

**S-08. Булевий вираз не порівнюють із `true` чи `false`.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** порівняння нічого не додає, а `== false` легко
  пропустити під час читання.
- **Порушення:** `if (f == true && sum1 > 1000)`
- **Дотримання:** `if (isRegularCustomer && total > RegularDiscountThreshold)`
- **Перевірка:** IDE0100, error.

**S-09. Умову з трьох і більше операндів виносять в іменовану змінну або метод.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** ім’я `isOverdue` пояснює, навіщо перевіряють п’ять
  умов, і дає змогу перевірити саме цю логіку тестом.
- **Порушення:** `if ((s == 0 || s == 1) && d < today && !paid)`
- **Дотримання:** `bool isOverdue = ticket.IsOverdueOn(reportDate);`
- **Перевірка:** R-09.

**S-10. `foreach` — за замовчуванням; `for` — лише коли потрібен індекс.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** `foreach` не дає вийти за межі колекції й не потребує
  доступу за індексом `lines[i]` у кожному рядку тіла.
- **Порушення:** `for (int i = 0; i < ln.Count; i++) { sum += ln[i].Amount; }`
- **Дотримання:** `foreach (RepairWork line in lines) { sum += line.Amount; }`
- **Перевірка:** R-09.

**S-11. Цикломатична складність методу — не більше 12; від 9 рецензент пропонує розбиття.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** див. 5.2 і 5.3.
- **Порушення:** метод зі складністю 13.
- **Дотримання:** виділення методу (Extract Method) або таблиця рішень.
- **Перевірка:** CA1502 з порогом у `CodeMetricsConfig.txt`, error; R-08 для попереджувального порогу.

**S-12. Метод — до 30 рядків тіла; від 50 зміну не приймають.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** метод на 30 рядків вміщується на екран разом із
  викликом; найдовший метод ядра — `RepairTicketService.Pay` — має близько 25 рядків тіла.
- **Перевірка:** R-08.

**S-13. Метод — до 4 параметрів; від 6 параметри збирають в об’єкт.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** в успадкованому `Process` (ЛР3) було 11 параметрів, і
  кілька сусідніх параметрів одного типу легко переставити місцями при виклику;
  об’єкт `TotalRequest` з іменованими властивостями виключив таку помилку.
- **Порушення:** `Process(int id, string name, string email, ...)` на 11 параметрів.
- **Дотримання:** `TotalOf(TotalRequest request)`
- **Перевірка:** R-08.

**S-14. Клас — до 12 публічних членів, файл — до 300 рядків; від 20 членів і 500 рядків тип ділять.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** клас-Бог `RepairTicketManager` (ЛР4) поєднував сховище,
  ціни й сповіщення в одному файлі; після поділу за SOLID кожен клас має
  кілька членів і одну причину для зміни.
- **Перевірка:** R-08.

**S-15. Колекцію не змінюють під час її перебирання.**
- **Рівень:** ЗАБОРОНЕНО.
- **Обґрунтування:** `foreach` по `List<T>` кидає `InvalidOperationException`
  після першого видалення; у циклі `for` видалення зсуває індекси, і
  елемент пропускається без жодної помилки.
- **Порушення:** `foreach (RepairTicket t in _tickets) { if (t.Status == TicketStatus.Issued) { _tickets.Remove(t); } }`
- **Дотримання:** `_tickets.RemoveAll(t => t.Status == TicketStatus.Issued);`
- **Перевірка:** R-09.

**S-16. Тернарний оператор — для простого вибору одного значення; вкладений тернарний оператор заборонено.**
- **Рівень:** ЗАБОРОНЕНО (вкладений).
- **Обґрунтування:** `a ? b : c ? d : e` читається лише з дужками в голові;
  для трьох варіантів є `switch`-вираз.
- **Порушення:** `decimal rate = urgent ? 0.3m : high ? 0.15m : 0m;`
- **Дотримання:** `decimal rate = PriorityRules.SurchargeOf(priority);`
- **Перевірка:** R-09.

**S-17. LINQ або цикл — на вибір автора.**
- **Рівень:** ДОПУСКАЄТЬСЯ.
- **Обґрунтування:** `lines.Sum(l => l.Amount)` і цикл із накопиченням
  однаково зрозумілі; цикл зручніший, коли в тілі кілька гілок, як у `TotalOf`.
- **Перевірка:** не перевіряють.

## 5.2. Межі складності

Попередження — рецензент пропонує спрощення, але зміну можна прийняти.
Зупинка — для складності зміну не пропускає збірка (CA1502), для решти метрик
рецензент не приймає зміну без коментаря з причиною відступу.

| Метрика | Попередження (огляд) | Зупинка | Дія при перевищенні | Перевірка |
|---|---|---|---|---|
| цикломатична складність методу | 9 | 13 і більше | виділити метод, `switch`-вираз | CA1502 (поріг 12), R-08 |
| глибина вкладеності | 3 | 4 | сторожова умова, виділення методу | R-09 |
| рядків у тілі методу | 30 | 50 | декомпозиція | R-08 |
| параметрів методу | 4 | 6 | об’єкт-параметр | R-08 |
| публічних членів класу | 12 | 20 | виділення класу | R-08 |
| рядків у файлі | 300 | 500 | поділ типу | R-08 |

Чому поріг складності саме 12. На скріні аналізатора з тимчасовим порогом 2
найскладніші методи ядра мають 9: `WorkOrder.IsValid` (вісім умов через `&&`)
і `RepairLineParser.TryParse` (розбір трьох полів із межами). Парсер вводу
природно має одну гілку на кожну причину відмови, тож 9–11 — нормальна
складність для барикади, і ламати її на дрібні методи лише заради метрики
шкідливо. Поріг 12 лишає парсерам запас у три гілки, а будь-який метод бізнес-логіки
з 13 гілками вже явно поєднує кілька правил. Від 9 рецензент пропонує розбиття
на огляді, але не блокує зміну.

## 5.3. Ручний підрахунок складності

Цикломатична складність = 1 + кількість точок розгалуження (`if`, `else if`,
`case`, цикл, `&&`, `||`, `?:`, `??`). Для `WorkOrder.CalculateTotal`:

| Конструкція | Рядок | Внесок |
|---|---|---|
| початкове значення | — | 1 |
| `for` за позиціями | `for (int i = 0; i < _lines.Count; i++)` | +1 |
| `if` постійного клієнта | `if (isRegularCustomer && total > RegularDiscountThreshold)` | +1 |
| `&&` у тій самій умові | | +1 |
| `else if` великого замовлення | `else if (total > LargeOrderThreshold)` | +1 |
| `if` гуртової знижки | `if (lineCount > BulkLineCount)` | +1 |
| `if` від’ємної суми | `if (total < 0)` | +1 |
| **разом** | | **7** |

Аналізатор CA1502 для цього методу показав «cyclomatic complexity of '7'» —
значення збігається. Так само вручну: `RepairTicketService.Pay` — 1 + три
`if` = 4 (інструмент: 4); `PriorityRules.TotalOf` — 1 + `foreach` + `if` = 3
(інструмент: 3).

## 5.4. Пари прикладів

**Пара 21. Вкладені умови замість сторожових (S-01, S-03).**

```csharp
// ПОГАНО
public decimal TotalOf(RepairTicket ticket)
{
    if (ticket != null)
    {
        if (ticket.Lines != null)
        {
            if (ticket.Lines.Count > 0)
            {
                return PriorityRules.TotalOf(ticket.Lines, ticket.Priority);
            }
        }
    }

    return 0;
}
```

```csharp
// ДОБРЕ
public decimal TotalOf(RepairTicket ticket)
{
    ArgumentNullException.ThrowIfNull(ticket);

    return PriorityRules.TotalOf(ticket.Lines, ticket.Priority);
}
```

Глибина вкладеності впала з 3 до 0; `null` став винятком, а не мовчазним
нулем, який проявиться пізніше як безкоштовний ремонт. Порожня заявка й так
дає 0,00 за правилом `TotalOf`.

**Пара 22. Ланцюг `if` замість `switch`-виразу (S-04, S-05, X-03).**

```csharp
// ПОГАНО
int days;
if (priority == TicketPriority.Urgent) days = 1;
else if (priority == TicketPriority.High) days = 2;
else if (priority == TicketPriority.Normal) days = 5;
else days = 10;
```

```csharp
// ДОБРЕ
int days = priority switch
{
    TicketPriority.Low => LowDays,
    TicketPriority.Normal => NormalDays,
    TicketPriority.High => HighDays,
    TicketPriority.Urgent => UrgentDays,
    _ => throw new ArgumentOutOfRangeException(nameof(priority), priority, "Невідомий пріоритет."),
};
```

Ланцюг мовчки дає 10 днів для будь-якого невідомого значення; `switch`-вираз
читається як рядки таблиці 1 специфікації і кидає виняток на помилку.

**Пара 23. Довга умова без імені (S-08, S-09).**

```csharp
// ПОГАНО
if (id != null && id != "" && cl != null && cl.Length > 2 && ln.Count > 0 && ln.Count < 100 && st >= 0 && st <= 3)
return true;
else
return false;
```

```csharp
// ДОБРЕ
bool hasHeader = !string.IsNullOrEmpty(Id)
    && CustomerName.Length >= MinCustomerNameLength;
bool hasValidLines = _lines.Count is > 0 and < MaxLineCount;

return hasHeader && hasValidLines;
```

Вісім умов в одному рядку довжиною 120 символів неможливо перевірити
поглядом; дві іменовані частини пояснюють, що саме перевіряють, а
`if … return true; else return false;` замінено самим виразом.
