# 7. Чекліст огляду, порівняння, порядок змін

## 7.1. Чекліст огляду коду

Чекліст винесено в окремий файл `docs/review-checklist.md`: 18 пунктів
R-01…R-18 у дев’яти категоріях. У ньому немає пунктів, які вже перевіряє
машина: відступи, регістр імен, дужки, порядок `using`, наявність
XML-коментарів і складність понад 12 зупиняють збірку самі. Людина дивиться
те, чого машина не бачить: зміст імен, магічні числа, правила предметної
області, обробку помилок, тести.

Два правила культури огляду (наведені й у чеклісті): зауваження формулюють
до коду, а не до автора; кожне зауваження містить конкретну дію.

### Відступи від обох джерел

**1. Статичні поля без префікса `s_`.** Обидва джерела вимагають `s_` для
статичних полів, ми — `_` для всіх приватних. Причина: у ядрі RepairService
немає змінюваних статичних полів, а незмінні значення оформлено як `const`
або статичну властивість (D-08). Друга схема префіксів дала б ще одне правило
іменування, яке нічого не розрізняє в нашому коді. Ціна — якщо змінюване
статичне поле колись з’явиться, його не буде видно з імені; тоді правило
переглянуть записом у журналі рішень.

**2. Фігурні дужки навіть для одного оператора.** Настанови dotnet/runtime
дозволяють однорядковий блок без дужок, Microsoft Learn явної вимоги не
ставить. Ми вимагаємо дужки завжди, рівень error. У навчальному проєкті
зміни вносять швидко, і найпоширеніша помилка — дописати другий оператор під
`if` без дужок: він виконуватиметься завжди. Саме так виглядав рядок
`if (kolvo > 10) sum1 = sum1 - 100;` в успадкованому коді ЛР2. Ціна правила —
два рядки, ціна помилки — дефект, якого не видно під час читання.

**3. Межа рядка 100 символів.** Жодне з джерел не встановлює жорсткої межі
для коду. Ми обрали 100: на екрані 1920 пікселів у VS Code з панеллю
провідника й порівнянням версій у дві колонки видно близько 105 символів у
колонці, тож огляд змін на GitHub і в редакторі обходиться без горизонтального
прокручування. Рівень лише РЕКОМЕНДОВАНО, бо аналізатор .NET довжину не
перевіряє, а рядок з адресою в коментарі не скоротиш.

**4. Українська мова коментарів і документації.** Обидва джерела пишуть
англійською, бо їхній код читає міжнародна спільнота. Код RepairService
читають і оцінюють україномовні розробники й викладач, а терміни домену
(«заявка», «дедлайн», «надбавка») в українській документації однозначні.
Ідентифікатори при цьому англійські, тож код лишається звичним для
інструментів і бібліотек. Ціна — придушені правила SA1623 і SA1642, що
вимагають англійських шаблонних фраз.

## 7.3. Порядок внесення змін до стандарту

1. **Хто пропонує.** Будь-який учасник команди відкриває pull request у гілці
   `standard/<коротка-назва>` зі зміною `CODING_STANDARD.md` або файлу розділу
   й, якщо потрібно, `.editorconfig`.
2. **Що містить пропозиція.** Формулювання правила за шаблоном 1.4; обґрунтування;
   пару «погано / добре» з коду RepairService; спосіб машинної перевірки або
   пункт чеклісту; оцінку вартості приведення наявного коду (кількість
   порушень, яку покаже збірка, і години).
3. **Хто ухвалює.** Власник стандарту після обговорення в pull request.
   Принцип: правило приймають, якщо воно запобігає реальному дефекту або
   суперечці, що вже траплялися в історії репозиторію; «так красивіше» не є
   підставою.
4. **Як фіксують.** Новий запис журналу рішень `docs/decisions/ADR-NNN-<назва>.md`
   із номером, датою, статусом, контекстом, рішенням і наслідками; у тексті
   правила — посилання на запис.
5. **Версія стандарту.** Семантичне версіювання: нове правило рівня
   ДОПУСКАЄТЬСЯ чи РЕКОМЕНДОВАНО або уточнення тексту — молодша версія
   (2.0.0 → 2.1.0); підвищення рівня правила або нове правило ОБОВ’ЯЗКОВО
   чи ЗАБОРОНЕНО — старша версія (2.x → 3.0.0); виправлення помилки в
   прикладі — латка (2.0.1).
6. **Перехідний період.** Наявний код не переписують одномоментно. Якщо нове
   правило ламає збірку, порушення в старому коді заносять у
   `docs/tech-debt.md`, а правило вмикають як `suggestion` до кінця
   перехідного періоду — чотири тижні або кінець семестру, що настане раніше.
   Діє правило бойскаута: файл, якого торкнулися, лишають чистішим, ніж він
   був. Так у цій версії погашено два зайві `using` у `src/Legacy`.
7. **Скасування шкідливого правила.** Той самий шлях, що й зміна: pull request
   із записом ADR зі статусом «скасовує ADR-NNN» і поясненням, який дефект чи
   втрату часу правило спричинило. Номер правила більше не використовують;
   у тексті стандарту лишається рядок «скасовано, див. ADR-NNN».
