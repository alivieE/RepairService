# 3. Форматування, структура файлу, коментарі

## 3.1. Форматування й структура файлу

**F-01. Відступ — чотири пробіли; для `.csproj`, `.props`, `.json`, `.yml` — два.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** табуляція в різних редакторах має різну ширину, і
  вирівняний код «розлазиться» в огляді змін на GitHub. Чотири пробіли — типове
  значення шаблонів .NET; у XML і YAML вкладеність глибша, тому два.
- **Порушення:** рядок із символом табуляції на початку.
- **Дотримання:** чотири пробіли на рівень.
- **Перевірка:** `.editorconfig` `indent_style = space`, `indent_size = 4`; IDE0055, error.

**F-02. Довжина рядка — до 100 символів.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** на екрані 1920 пікселів у VS Code з відкритою панеллю
  провідника й порівнянням версій у дві колонки шрифтом 14 пунктів видно
  близько 105 символів у кожній колонці; межа 100 гарантує, що огляд змін
  обходиться без горизонтального прокручування. Довший рядок переносять за F-12.
  Рівень РЕКОМЕНДОВАНО, бо жоден аналізатор .NET довжину рядка не перевіряє,
  а рядки з URL у коментарі коротшими не зробиш.
- **Порушення:** рядок на 130 символів з умовою й викликом методу.
- **Дотримання:** перенесення після відкривної дужки, кожен аргумент на своєму рядку.
- **Перевірка:** `max_line_length = 100` (вертикальна лінія в редакторі), R-08.

**F-03. Файл — UTF-8, закінчується символом нового рядка, без пробілів у кінці рядків.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** коментарі й рядки українською ламаються в іншому
  кодуванні; відсутній кінцевий рядок і зайві пробіли дають «шумові» зміни в
  огляді, коли інший редактор їх виправляє.
- **Порушення:** файл без кінцевого рядка (`\ No newline at end of file` у diff).
- **Дотримання:** кінцевий рядок є, пробілів у кінці рядків немає.
- **Перевірка:** `charset`, `insert_final_newline`, `trim_trailing_whitespace`; SA1028, error;
  FINALNEWLINE у `dotnet format`.

**F-04. Кінці рядків нормалізує Git; у робочій копії допускаються CRLF і LF.**
- **Рівень:** ДОПУСКАЄТЬСЯ.
- **Обґрунтування:** розробка ведеться на Windows, конвеєр — на Linux. Якщо
  записати `end_of_line = lf`, то `dotnet format` на Windows вимагатиме
  переписати кожен файл, отриманий з `core.autocrlf = true`. У репозиторії
  кінці рядків однакові завдяки Git, тому в `.editorconfig` ключ не задано.
- **Перевірка:** зауважень не роблять.

**F-05. Фігурні дужки — стиль Allman.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** відкривна дужка на окремому рядку вирівнюється із
  закривною, тому межі блоку видно без підсвічування. Це типовий стиль .NET.
- **Порушення:** `if (amount < total) {`
- **Дотримання:** `if (amount < total)` і `{` на наступному рядку.
- **Перевірка:** `csharp_new_line_before_open_brace = all`; IDE0055, error.

**F-06. Фігурні дужки обов’язкові навіть для одного оператора.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** найпоширеніша помилка — дописати другий оператор під
  `if` без дужок: він виконуватиметься завжди. Ціна правила — два рядки,
  ціна помилки — дефект, якого не видно під час читання.
- **Порушення:** `if (kolvo > 10) sum1 = sum1 - 100;`
- **Дотримання:** тіло в дужках на окремих рядках.
- **Перевірка:** `csharp_prefer_braces = true:error`; IDE0011, SA1503, error.

**F-07. Порожні рядки: один між членами класу й після закритого блоку; два поспіль заборонено.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** порожній рядок відділяє кроки алгоритму; два поспіль
  нічого не додають і вказують на видалений шматок коду.
- **Порушення:** два методи без порожнього рядка між ними.
- **Дотримання:** рівно один порожній рядок.
- **Перевірка:** SA1516, SA1507, error.

**F-08. Один тип на файл.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** невеликі файли легше переглядати в огляді змін, а
  історія Git показує зміни конкретного типу. Ім’я файлу — за N-18.
- **Порушення:** `FakeRepairTicketRepository` і `StubPricingPolicy` в одному файлі тестів.
- **Дотримання:** кожен дублер у власному файлі.
- **Перевірка:** SA1402, error.

**F-09. Порядок членів класу: константи → поля → конструктори → властивості → методи;
усередині групи `public` перед `private`, статичні перед екземплярними.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** читач шукає контракт класу (публічні члени) згори, а
  деталі реалізації — знизу. Однаковий порядок у всіх файлах прибирає пошук.
- **Порушення:** приватний метод між конструктором і властивостями.
- **Дотримання:** порядок як у `RepairTicketService`.
- **Перевірка:** SA1201, SA1202, SA1204, error.

**F-10. Простір імен файлового рівня.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** файл містить один тип (F-08), тому блок простору імен
  лише додає рівень відступу всьому файлу.
- **Порушення:** `namespace RepairService.Core { ... }`
- **Дотримання:** `namespace RepairService.Core;`
- **Перевірка:** `csharp_style_namespace_declarations = file_scoped:error`; IDE0161.

**F-11. `using` — поза простором імен, `System` першими, невживаних немає.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** список залежностей файлу видно відразу; невживаний
  `using` вводить в оману щодо того, від чого залежить файл. Під час
  запровадження правила воно знайшло два зайві `using` в успадкованому модулі.
- **Порушення:** `using System;` при ввімкнених `ImplicitUsings`.
- **Дотримання:** лише ті `using`, без яких файл не скомпілюється.
- **Перевірка:** `dotnet_sort_system_directives_first`; IDE0065, IDE0005, error.

**F-12. Перенесення: аргументи — або всі в рядку, або кожен на своєму рядку;
логічний оператор — на початку нового рядка.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** змішане перенесення ховає аргумент у кінці рядка; оператор
  `||` чи `&&` на початку рядка показує зв’язок умов, не дочитуючи попередній рядок.
- **Порушення:** `new DomainRuleException("ticket.amount", message,` і `inner)` на наступному рядку.
- **Дотримання:** як у `RepairWorkParser.Parse`: `|| count <= 0)` з нового рядка.
- **Перевірка:** SA1116, SA1117, error; положення оператора — R-08.

**F-13. Регіони `#region` заборонено.**
- **Рівень:** ЗАБОРОНЕНО.
- **Обґрунтування:** регіон ховає код, а потреба в ньому означає, що клас
  завеликий і його час ділити (S-14).
- **Порушення:** `#region Helpers` … `#endregion`
- **Дотримання:** допоміжні методи — в окремому класі.
- **Перевірка:** SA1124, error.

**F-14. В ініціалізаторі об’єкта кожна властивість на окремому рядку; кома після останньої допускається.**
- **Рівень:** ДОПУСКАЄТЬСЯ.
- **Обґрунтування:** кінцева кома скорочує diff під час додавання властивості,
  але її відсутність не шкодить; тому SA1413 придушено.
- **Перевірка:** зауважень не роблять.

**F-15. Тіло-вираз `=>` для однорядкових членів.**
- **Рівень:** ДОПУСКАЄТЬСЯ.
- **Обґрунтування:** `public decimal Amount => Quantity * UnitPrice;` коротше
  без втрати ясності; для логіки довшої за рядок — звичайне тіло.
- **Перевірка:** `csharp_style_expression_bodied_*`, silent.

**F-16. Один оператор на рядок.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** налагоджувач ставить точку зупину на рядок; два оператори
  в рядку не можна пройти окремо, а в diff зміна одного виглядає як зміна обох.
- **Порушення:** `t[0] = s; t[1] = k.ToString(); t[2] = c.ToString();`
- **Дотримання:** кожне присвоєння на своєму рядку.
- **Перевірка:** SA1107, error.

**F-17. Пробіли навколо бінарних операторів і після коми.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** `total+total*VatRate` читається гірше за
  `total + total * VatRate`; єдиний вигляд дає `dotnet format`.
- **Перевірка:** `csharp_space_around_binary_operators`, `csharp_space_after_comma`; IDE0055, error.

### Приклад: форматування (F-01, F-05, F-06, F-16)

```csharp
// ПОГАНО
public bool Chg(int n)
{
if (st == 0 && n == 1) { st = 1; return true; }
   if (st == 1 && n == 2) { st = 2; return true; }
return false;   // не можна
}
```

```csharp
// ДОБРЕ
public bool TryChangeStatus(int newStatus)
{
    if (Status == StatusNew && newStatus == StatusApproved)
    {
        Status = StatusApproved;
        return true;
    }

    return false;
}
```

Відступи «стрибають», тож вкладеність доводиться рахувати за дужками; два
оператори в рядку не можна пройти налагоджувачем окремо.

## 3.2. Коментарі та XML-документація

**C-01. Закоментований код у гілці, що йде на злиття, заборонено.**
- **Рівень:** ЗАБОРОНЕНО.
- **Обґрунтування:** для історії є Git; закоментований фрагмент ніхто не
  наважується видалити, і він роками лишається в коді.
- **Порушення:** `// if (sum1 > 500) { sum1 = sum1 - 50; } // стара знижка`
- **Дотримання:** рядок видалено; стару знижку знаходять у `git log -S`.
- **Перевірка:** R-15.

**C-02. Коментар, що дублює код, заборонено.**
- **Рівень:** ЗАБОРОНЕНО.
- **Обґрунтування:** такий коментар нічого не пояснює, а після зміни коду
  починає йому суперечити.
- **Порушення:** `id = a; // ставимо id`
- **Дотримання:** `Id = id;` без коментаря.
- **Перевірка:** R-15.

**C-03. Замість коментаря-виправдання поганого імені ім’я перейменовують.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** коментар біля оголошення не видно в місцях виклику.
- **Порушення:** `public int st = 0; // 0-нова,1-погодж,2-викон,3-скасов`
- **Дотримання:** `public TicketStatus Status { get; private set; }`
- **Перевірка:** R-15.

**C-04. Коментар оновлюють разом із кодом; застарілий коментар видаляють.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** читач вірить коментарю більше, ніж коду, і помиляється.
  Хто змінює код, той оновлює коментар у тому самому коміті.
- **Порушення:** `/// Знижка 5 %` над методом, що дає 10 %.
- **Дотримання:** коментар посилається на константу: «знижка `RegularDiscountRate`».
- **Перевірка:** R-15.

**C-05. Позначка `TODO` — лише з номером запису реєстру технічного боргу й автором.**
- **Рівень:** ЗАБОРОНЕНО (без номера й автора).
- **Обґрунтування:** «TODO» без запису в реєстрі ніхто не планує, і він живе
  вічно. Реєстр — `docs/tech-debt.md` (ЛР6), номери `TD-NN`.
- **Порушення:** `// TODO: переробити`
- **Дотримання:** `// TODO(TD-10, Новиков): перевести WorkOrder на IClock`
- **Перевірка:** `git grep -n "TODO" | findstr /v "TODO(TD-"` перед комітом, R-16.

**C-06. Коментар пояснює «чому», а не «що».**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** «що» видно з коду; причину рішення — ні, і саме її шукають
  через півроку.
- **Порушення:** `// множимо ціну на кількість`
- **Дотримання:** `// ПДВ нараховується на суму вже після всіх знижок`
- **Перевірка:** R-13.

**C-07. XML-документація обов’язкова для всіх видимих членів Core і App.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** підказка IntelliSense — перше, що бачить автор виклику.
  У тестових проєктах документацію не вимагаємо: назва тесту сама описує
  сценарій (N-16), тому там CS1591 вимкнено з обґрунтуванням.
- **Порушення:** публічний метод без `/// <summary>`.
- **Дотримання:** зразок нижче.
- **Перевірка:** CS1591, SA1600, SA1601, SA1602, error.

**C-08. Обов’язкові теги: `summary`; `param` для кожного параметра; `returns` для
не-`void`; `exception` для кожного винятку, який метод кидає свідомо.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** без `exception` автор виклику не знає, що `Pay` кидає
  `DomainRuleException`, і не обробляє його.
- **Порушення:** `Pay` без `<exception cref="DomainRuleException">`.
- **Дотримання:** зразок нижче.
- **Перевірка:** SA1611, SA1615, error; тег `exception` — R-12.

**C-09. `summary` описує призначення, а не реалізацію; для запиту зазначають відсутність побічних ефектів.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** реалізація змінюється, призначення — ні.
- **Порушення:** `/// Цикл по позиціях і множення ціни на кількість.`
- **Дотримання:** `/// Обчислює вартість заявки. Не змінює стан заявки.`
- **Перевірка:** R-12.

**C-10. Коментарі й документація — українською, ідентифікатори — англійською.**
- **Рівень:** РЕКОМЕНДОВАНО.
- **Обґрунтування:** команда україномовна, а терміни предметної області
  (пріоритет, дедлайн, видача) точніше передає рідна мова. Через це придушено
  SA1623 і SA1642, які вимагають англійських зачинів «Gets…».
- **Порушення:** `/// Gets the ticket total.`
- **Дотримання:** `/// Вартість заявки, грн.`
- **Перевірка:** R-12.

**C-11. Посилання на типи в документації — через `<see cref="..."/>`.**
- **Рівень:** ДОПУСКАЄТЬСЯ.
- **Обґрунтування:** `cref` перевіряє компілятор і оновлює перейменування, але
  в короткому коментарі звичайна назва теж зрозуміла.
- **Перевірка:** зауважень не роблять.

**C-12. Файл документації генерують усі проєкти, крім `src/Legacy`.**
- **Рівень:** ОБОВ’ЯЗКОВО.
- **Обґрунтування:** без `GenerateDocumentationFile` компілятор не видає CS1591,
  і правило C-07 перевіряла б лише людина. Властивість задано один раз у
  `Directory.Build.props` з умовою для Legacy.
- **Перевірка:** `Directory.Build.props`, A-02.

### Пари прикладів

**Пара 13. Коментарі, що дублюють код (C-02).**

```csharp
// ПОГАНО
// конструктор
public zayavka(string a, string b)
{
    id = a;              // ставимо id
    cl = b;              // ставимо cl
    dt = DateTime.Now;   // ставимо дату
}
```

```csharp
// ДОБРЕ
public RepairTicket(int id, int customerId, string deviceModel, DateOnly createdAt)
{
    Id = id;
    CustomerId = customerId;
    DeviceModel = deviceModel;
    CreatedAt = createdAt;
}
```

Коментарі переказують код словами; після перейменування полів вони
залишилися б зі старими назвами.

**Пара 14. Закоментований код (C-01).**

```csharp
// ПОГАНО
// if (sum1 > 500) { sum1 = sum1 - 50; } // стара знижка
if (f == true && sum1 > 1000) { sum1 = sum1 * 0.9m; }
```

```csharp
// ДОБРЕ
if (isRegularCustomer && total > RegularDiscountThreshold)
{
    total *= 1m - RegularDiscountRate;
}
```

Читач не знає, чи стара знижка ще діє десь в іншому місці і чи її
збираються повернути. Історію зберігає Git.

**Пара 15. Коментар «чому» (C-06).**

```csharp
// ПОГАНО
// додаємо ПДВ
total += total * VatRate;
```

```csharp
// ДОБРЕ
// ПДВ нараховується на суму вже після всіх знижок
total += total * VatRate;
```

Перший коментар повторює код. Другий фіксує бізнес-правило: перестановка
рядків змінила б суму, і коментар про це попереджає.

**Пара 16. XML-документація (C-07, C-08, C-09).**

```csharp
// ПОГАНО
/// <summary>Оплата.</summary>
public void Pay(int ticketId, decimal amount)
```

```csharp
// ДОБРЕ
/// <summary>Приймає оплату при видачі пристрою: Ready → Issued.</summary>
/// <param name="ticketId">Номер заявки.</param>
/// <param name="amount">Сплачена сума, грн.</param>
/// <exception cref="DomainRuleException">
```
